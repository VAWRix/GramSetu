# GramSetu — Security, Authentication & Cryptographic Integrity

**Project Title:** GramSetu – A Digital Gram Panchayat Information and Governance Portal  
**Security Baseline:** Guidelines for Indian Government Websites (GIGW 3.0), OWASP Top 10 (2021)  

---

## 1. Authentication & Multi-Factor Architecture

GramSetu enforces a strict two-factor authentication pipeline for all administrative staff accessing the CMS (`/cms`):

```
+------------------------------------------------------------------------------------+
|                         MFA VERIFICATION LIFECYCLE                                 |
+------------------------------------------------------------------------------------+
| 1. Primary Auth   : Email + PBKDF2 Password verified against identity_user        |
| 2. Challenge Gen  : 6-digit numeric token generated by EmailDevice (django-otp)    |
| 3. Transport      : Delivered to staff email (Console in Dev, SMTP in Prod)        |
| 4. Security Bounds: 300s expiration, 60s cooldown between resends, 5 max attempts  |
| 5. Token Invalidation: Token cleared (None) immediately upon verification          |
| 6. Session Binding: Session cookie (sessionid) issued with HttpOnly + SameSite=Lax |
+------------------------------------------------------------------------------------+
```

### Password Storage Security
- Passwords are encrypted using **PBKDF2 SHA-256** with **600,000 iterations** and unique per-user cryptographic salts via `django.contrib.auth.hashers.make_password`.
- Plaintext passwords are never persisted to disk or logged.

### Brute-Force & Credential Stuffing Defense
- Failed login attempts are tracked per IP and email.
- 5 consecutive failed attempts trigger an automatic **15-minute account lockout** (returning HTTP 423 Locked).

## 2. Role-Based Access Control (RBAC) & Democratic Separation

```
+---------------------------------------------------------------------------------------------------------+
|                                    ROLE PERMISSIONS & SEPARATION OF DUTIES                              |
+---------------------------------------+---------------------+---------------------+---------------------+
| ADMINISTRATIVE CAPABILITY             | SUPER ADMIN         | OPERATOR            | CITIZEN / PUBLIC    |
|                                       | (Gramsevak)         | (Computer Operator) | (Unauthenticated)   |
+---------------------------------------+---------------------+---------------------+---------------------+
| Browse Public Portal                  | Yes                 | Yes                 | Yes                 |
| Download Disclosed Records            | Yes                 | Yes                 | Yes                 |
| Access Staff CMS Portal (`/cms`)      | **Yes**             | **Yes**             | **Forbidden (401)** |
| Draft Notices, Pages & Schemes        | Yes                 | Yes                 | No                  |
| Upload Document Versions (PDF)        | Yes                 | Yes                 | No                  |
| View Review Queue (`/cms/pending/`)   | Yes                 | Yes (Read-Only)     | No                  |
| **Approve Revisions**                 | **Yes**             | **Forbidden (403)** | No                  |
| **Reject Revisions with Justification**| **Yes**             | **Forbidden (403)** | No                  |
| **Publish Content to Live Portal**    | **Yes**             | **Forbidden (403)** | No                  |
| **Self-Approval Execution**           | **Forbidden (403)** | **Forbidden (403)** | No                  |
| **System Login Account**              | **Yes**             | **Yes**             | **Sarpanch: NO**    |
+---------------------------------------+---------------------+---------------------+---------------------+
```

### The Sarpanch Democratic Isolation Rule
- The Sarpanch is an elected political dignitary representing the Gram Panchayat.
- By democratic constitutional design, administrative record-keeping is the legal responsibility of the appointed Gramsevak. Denying technical login access to political figures prevents partisan tampering with official gazettes and ensures clear statutory accountability.

## 3. Session Security & HTTP Security Headers

- **30-Minute Inactivity Expiration**: Sessions expire after 1800 seconds (`SESSION_COOKIE_AGE = 1800`).
- **Browser-Close Invalidation**: `SESSION_EXPIRE_AT_BROWSER_CLOSE = True`.
- **Cookie Security**:
  - `SESSION_COOKIE_HTTPONLY = True`: Blocks JavaScript access to session tokens.
  - `SESSION_COOKIE_SAMESITE = 'Lax'`: Mitigates Cross-Site Request Forgery (CSRF).
  - `CSRF_COOKIE_HTTPONLY = True`: Protects CSRF tokens.
- **Mandatory GIGW 3.0 Headers**:
  - `X-Frame-Options: DENY`: Blocks clickjacking and UI redressing.
  - `X-Content-Type-Options: nosniff`: Prevents MIME-type sniffing.
  - `X-XSS-Protection: 1; mode=block`: Activates browser XSS filters.

## 4. Protected Storage & Cryptographic SHA-256 Media Integrity

- **Filesystem Isolation**: Disclosed PDF orders and photo gallery images are stored in dedicated directories located outside the web root (`private_docs/` and `private_media/gallery/`). Files cannot be accessed directly via static URLs.
- **Controlled Streaming Views**: Files are streamed through Django views (`document_version_download_view`, `gallery_image_serve_view`) which verify disclosure status and set safe `Content-Disposition` headers.
- **Cryptographic SHA-256 Checksum Verification**:
  1. Upon file upload, Django calculates a 256-bit SHA-256 checksum saved in `checksum_sha256`.
  2. Prior to streaming files to public users, the checksum is verified against the stored binary. If the file on disk has been tampered with or corrupted, the system blocks the download.

## 5. Security Checklist for Production Deployment

Before moving from development to production:
1. Terminate TLS certificates (HTTPS) via an Nginx reverse proxy.
2. Set `DJANGO_DEBUG=False` in production environment files.
3. Configure live SMTP credentials for email OTP delivery (development uses console backend).
4. Rotate `DJANGO_SECRET_KEY` and all database passwords using strong, randomly generated keys.
5. Set `DB_ROLE=app` for normal runtime application processes.
